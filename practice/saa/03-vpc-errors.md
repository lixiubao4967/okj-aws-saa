## 错题 11：NACL 无状态 —— 出站临时端口

**场景：** 自建 NACL，入站放开 443，用户访问 HTTPS 仍失败。漏了什么？

**我的答案：** D) 出站放开 443　**正确答案：** A) 出站放开临时端口 1024-65535

### 错因
以为「入站 443 / 出站 443」对称。**NACL 规则匹配的是【目的端口】，而响应包的目的端口不是 443。**

### 四元组摊开看

```
① 客户端 → 服务器（入站）
   源 1.2.3.4:54321  →  目的 10.0.1.5:443
   NACL 入站规则看【目的端口 443】 ✅

② 服务器 → 客户端（出站响应）
   源 10.0.1.5:443   →  目的 1.2.3.4:54321
   NACL 出站规则看【目的端口 54321】 ❌ 不是 443
```

54321 是客户端 OS 随机挑的**临时端口**，每次连接都不同 → 只能放开整个范围。

### 临时端口范围

| 客户端类型 | 范围 |
|---|---|
| Linux 内核 | 32768–60999 |
| Windows Server 2003 | 1025–5000 |
| Windows Server 2008+ | 49152–65535 |
| **ELB / NAT GW / Lambda** | **1024–65535** |

> 🔑 客户端五花八门 → **AWS 官方建议 NACL 出站直接放开 `1024-65535`**

### 为什么 SG 不用管这些
SG **有状态**：记住「这条连接是我允许进来的」，响应流量自动放行，不看端口。
这就是「有状态 / 无状态」的实际差别。

### 🚨 考场识别信号
题干出现「自定义 NACL」+「入站规则看起来对」+「连接失败/超时」→ **99% 是漏了出站临时端口**。
若题干说的是 Security Group 配错 → 绝不会是这个原因。

### 记法一句话
> **NACL 只认「目的端口」。请求的目的端口是服务端口，响应的目的端口是客户端的随机端口。**
